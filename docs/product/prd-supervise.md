## 一、背景与目标

### 1.1 产品定位

学习观察与行为采集模块（系统能力 5.1 数据采集）是读学系统的**物理感知源头与事实输入基座**。

它通过架设在书桌侧后方的闲置 Android 设备（读学Eye）或学生伴学设备，在学生执行学习任务期间，以**极低功耗、稀疏定时抓拍（每 15 秒一帧）、预签名直传 OSS** 的方式静默记录学习桌面与行为动作，为后续的 AI 启发答疑、结果评估双轨复盘及长期成长模型提供客观、中立的事实数据底座。

### 1.2 核心设计原则

1. **安静在场，坚决不做“实时电子监工”**：
   - **严禁提供实时视频直播/推流**：系统不向 Guardian 提供任何形式的实时监控画面，彻底消除“被偷窥感”与亲子信任危机；
   - **严禁实时告警打扰**：采集过程中界面与设备不发出任何“分心警告”“专注打分”等红字或蜂鸣声，保护学生沉浸心流。
2. **抓拍而非推流，极致轻量与零门槛**：
   - 设备只做“定时抓拍单张 JPEG（640×480）直传 OSS”，上行带宽仅约 80kbps；
   - 零额外硬件成本，家里闲置 Android 手机（Android 8.0+）即可稳定挂机，发热低、耗电低。
3. **机位内建隐私保护（Privacy by Design）**：
   - 机位严格规范为“**学生侧后方 45°、略高于头顶俯拍**”；
   - 取景范围仅包含桌面、双手、上半身与头部轮廓，**物理规避面部正脸特征**，送往云端的图像天然脱敏。
4. **公开透明，严禁隐蔽运行**：
   - 处于观察状态时，设备界面或状态栏必须持续明确显示“正在学习观察中”；
   - 学生对采集拥有知情权与控制权，可随时在端侧暂停或结束观察。
5. **端层职责单一，端云清晰解耦**：
   - 采集端设备（读学Eye）只负责“**扫码绑定、抓拍上传、本地排队、心跳上报**”，坚决不承担本地模型推理与复杂的时序平滑归并；
   - 特征解析与时序片段归并全部收口在服务端（`duxue-server`）后台流水线。

### 1.3 本期目标

- 实现 Android 采集端（读学Eye）与 Guardian 账号的 6 位邀请码/二维码极简扫码绑定；
- 实现固定间隔（默认 15 秒/帧）的静音后台抓拍与阿里云 OSS 预签名 PUT 直传管线；
- 实现本地 Room SQLite 持久化队列与断网自动补传机制（最大容纳 500 帧/约 2 小时）；
- 实现前台保活服务（Foreground Service `camera` 类型）与 WakeLock/WifiLock 电源锁管理；
- 实现每 60 秒一次的设备健康心跳上报，以及服务端连续 3 分钟失联向 Guardian 端推送掉线告警；
- 提供首次架设时的轻量取景校准辅助（侧后方 45° 指引、正脸规避校验）。

### 1.4 非目标

- 不做 RTMP/WebRTC 等任何形式的音视频持续推流与实时直播查看；
- 不在采集设备本地运行 VLM 或任何 AI 视觉分析推理；
- 不在第一期引入本地人形检测或帧差门控过滤（全量保留真实场景帧）；
- 不在当前阶段支持 iOS 设备作为长期挂机采集端（因系统后台相机权限严格限制）；
- 不做远程控制手机重启、远程抓拍等侵犯隐私的后门指令。

### 1.5 建议衡量指标

- **采集连续性（帧率完整率）**：会话进行期间，理论应采帧数与实际成功入库帧数的比例（目标 > 98%）；
- **设备保活稳定性**：在主流 Android 8.0~14.0 机型上，连续采集 3 小时无前台服务崩溃的比例 > 99.5%；
- **抓拍上传成功率**：单帧获取预签名 URL 并成功 PUT 上传至 OSS 的成功率 > 99.9%；
- **掉线告警准确率**：设备真实断网/关机后，Guardian 端在 3~5 分钟内收到掉线通知的触达率 > 95%。

### 1.6 名词解释

| 名词 | 解释 |
|------|------|
| 读学Eye（duxue-cam） | 安装在闲置 Android 手机上的专用采集端 App，负责定时抓拍上传与心跳维护 |
| 稀疏抓拍（Sparse Capture） | 按照固定时间间隔（如 15 秒）拍摄单张静态 JPEG 图像，而非持续录制视频 |
| 预签名直传（Pre-signed Upload） | 采集端向服务端申请有时效的 OSS 直传凭证，图片直接从设备 PUT 到 OSS，不经过业务 API 服务器中转 |
| 设备健康心跳（Device Heartbeat） | 采集端每 60 秒向服务端发送一次轻量健康数据（电量、网络、队列积压），用于判定在线状态 |
| 机位校准（Camera Calibration） | 引导用户将镜头调整至侧后方 45° 俯拍、物理规避正脸的交互流程 |

## 二、目标用户与核心场景

### 2.1 核心用户与角色分工

- **Ward（学生，被观察主体）**：在书桌前开始学习时开启采集；在透明、无实时监控压力的环境中专注学习；可随时暂停或结束。
- **Guardian（家长，设备管理者）**：在 App 端为闲置手机生成绑定码，协助调整机位；在日常中仅接收设备掉线或电量低通知，无法实时窥探画面。

### 2.2 核心用户旅程

```text
用户旅程：家庭闲置手机接入与学习观察全流程
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
【场景一：初次安装与扫码绑定】
Step 1：妈妈（Guardian）找出一台闲置的小米手机，下载安装“读学Eye”
Step 2：妈妈在自己的手机“读学App”点击【设备管理 → 添加采集设备】，屏幕展示 6 位邀请码及二维码
Step 3：用闲置手机打开“读学Eye”扫描二维码，系统自动完成设备鉴权并签发长效 device_token
Step 4：屏幕弹出【机位调整助手】：提示将手机架在侧后方 45° 支架上，俯拍桌面
        → 预览框显示桌面、双手清晰，画面中无正脸
        → 点击“确认摆放完成”，设备进入待命状态。

【场景二：日常伴学与静默采集】
Step 5：晚 19:10，小宇在书桌前准备写数学作业，点击开始学习
        → 读学Eye 自动进入“正在学习观察中”运行态（屏幕变暗防眩光，常驻提示“🟢 正在记录”）
        → 设备每隔 15 秒无声抓拍一张 JPEG 图片，直传阿里云 OSS
        → 采集期间，设备不发出任何声响，小宇感觉不到设备的存在，全神贯注写作业。

【场景三：偶发网络断开与自动补传】
Step 6：19:30，家里 Wi-Fi 路由器重启，读学Eye 检测到网络断开
        → 抓拍服务继续运行，新抓拍的照片自动暂存在手机内部 Room SQLite 队列中
Step 7：19:35，Wi-Fi 恢复连接，读学Eye 自动按时间戳顺序将积压的 20 张帧快速补传至 OSS
        → 整个断网过程数据零丢失，无需人工干预。

【场景四：学习结束与会话收尾】
Step 8：20:08，小宇在自己的学习平板上点击“完成今日学习”
        → 读学Eye 收到会话结束指令，停止抓拍服务，释放相机资源，进入低功耗待机态
        → 服务端即刻触发本会话全部图像帧的聚合分析，支撑小宇当晚的即时复盘。
```

### 2.3 关键异常路径

- **设备电量过低（< 15% 且未插充电器）**：
  - 采集端在心跳中上报低电量状态；
  - 服务端向 Guardian 发送温和提醒：“书桌采集手机电量较低，请插上充电器”；
- **设备异常掉线（断电/被系统杀进程）**：
  - 服务端连续 3 分钟未收到心跳，标记设备为 `offline`；
  - 向 Guardian 发送 App 推送：“书桌采集设备已离线，请检查手机是否息屏断电”；
- **网络长期中断导致本地队列超限**：
  - 若断网超过 2 小时且积压帧数达到 500 帧上限，本地采用先进先出（FIFO）原则丢弃最旧的帧，优先保证最新学习状态的留存；
- **学生中途离开书桌**：
  - 采集端不做本地空画面过滤，全量抓拍上传，由服务端 VLM 模型统一识别为 `seat_status: 离开`，客观记录时长。

## 四、功能需求（MoSCoW 架构）

### 4.1 Must Have（首期核心功能）

#### 4.1.1 设备绑定与凭证管理（Device Pairing & Auth）

- **绑定码生命周期**：
  - Guardian 端调用 `GenerateInviteCode` API 生成 6 位大写数字混合码与二维码，有效时长 10 分钟；
  - 绑定成功后邀请码立即失效；超期未绑定自动过期并支持一键刷新。
- **长效凭证鉴权**：
  - 采集端扫描二维码，调用 `BindDevice` 接口校验成功后，服务端签发 `device_token`；
  - `device_token` 必须通过 Android Keystore（`EncryptedSharedPreferences`）安全存储，后续所有数据上传均基于该 Token 鉴权。
- **机位校准辅助**：
  - 首次绑定后自动进入“机位校准”页面，临时开启 5 秒相机预览流；
  - 界面提供十字辅助线与取景框范围遮罩，明确提示：“请确保桌面、作业本与双手在框内，调整手机至侧后方 45°，避免正对人脸”。

#### 4.1.2 稀疏抓拍与预签名直传流水线（Capture & Upload Pipeline）

- **定时抓拍引擎**：
  - 采用 CameraX `ImageCapture` 用例，设置单帧捕获参数（格式：JPEG，分辨率：640×480，质量压缩比：80%）；
  - 抓拍间隔采用服务端下发配置（默认 15 秒/次），定时器基于 Kotlin Coroutines 精确调度。
- **OSS 预签名直传机制**：
  - 抓拍前或批量预取服务端下发的 OSS 预签名 PUT URL（有效期 5 分钟）；
  - 抓拍完成后，通过 OkHttp 异步执行 HTTP PUT 请求直接上传至阿里云 OSS 桶（Object 路径：`frames/{tenant_id}/{ward_id}/{date}/{frame_id}.jpg`）；
  - 上传成功后，向服务端 API 发送轻量元数据请求 `POST /frames`（仅包含 `frame_id`, `task_id`, `captured_at`, `oss_key`），**不经过 API 传输图像二进制流**。
- **全量无过滤策略**：
  - 第一期坚决不在端侧引入本地人形检测或帧差门控，所有抓拍帧全量直传入池，为服务端算法提供完整训练数据。

#### 4.1.3 断网保护与本地持久化队列（Offline Buffer & Sync）

- **Room SQLite 暂存**：
  - 当 HTTP 上传失败或系统处于离线状态时，将图片写入 App 内部私有存储沙盒（`context.filesDir/pending_frames/`），并在 Room 数据库 `pending_frames` 表中插入一条待传记录；
- **自动检测与恢复补传**：
  - 注册 Android `ConnectivityManager` 网络状态监听器，并在后台配合 WorkManager 兜底调度；
  - 网络恢复后，按时间戳升序逐一读取本地帧并执行预签名上传，上传成功后立即物理删除本地暂存文件与数据库记录；
- **FIFO 淘汰保护**：
  - 本地积压队列上限设定为 500 帧（对应约 2 小时离线数据）；
  - 当队列满时，自动剔除并物理删除时间戳最旧的 1 帧，保证新记录能持续写入，防止手机存储被撑爆。

#### 4.1.4 前台保活与健康心跳（Foreground Keep-Alive & Health）

- **Android 合规保活**：
  - 启动 `Foreground Service`，声明 `android:foregroundServiceType="camera"`；
  - 常驻系统通知栏显示：“读学Eye 正在为小宇记录学习状态”；
  - 持有 `WakeLock` 与 `WifiLock`，防止手机在息屏或待机时 CPU 休眠或 Wi-Fi 断开；
- **健康心跳上报**：
  - 采集端每 60 秒调用 `POST /devices/heartbeat`，上报当前电池电量、是否连接充电器、当前网络类型（Wi-Fi/蜂窝）、本地积压待传帧数；
  - 服务端刷新 `devices.last_heartbeat_at`。
- **掉线告警策略**：
  - 服务端定时巡检，若某设备在处于“采集中/待命”状态下连续 3 分钟未上报心跳，自动将状态置为 `offline`；
  - 服务端触发推送通道，向绑定的 Guardian 端 App 发送通知：“小宇的书桌采集设备已离线（可能没电或断网）”。

### 4.5 业务规则

1. **公开记录原则**：采集服务运行期间，屏幕与系统通知栏必须有明确的视觉状态指示，严禁隐蔽运行；
2. **直传隔离原则**：图片二进制流必须由设备直传 OSS，业务 API 服务器严禁作为图片中转代理，以保护后端性能；
3. **数据主权归属**：设备抓拍的所有图像数据归属当前家庭租户，90 天后自动从 OSS 物理删除，结构化分析特征长期保留；
4. **单向感知原则**：Guardian 端只能查看设备在线状态、电量与次日/当晚的聚合分析报告，严禁调取设备实时摄像头画面。

### 4.6 状态流转机

#### 4.6.1 采集端设备运行状态流转


## 六、质量与性能需求

| 指标维度 | 建议基线要求 | 备注 |
|---|---|---|
| 单帧抓拍与上传耗时 | P90 < 1.5s，P99 < 3.0s | 本地拍照到 OSS 写入完成 |
| 上行网络带宽占用 | 平均 < 80 kbps | 640×480 JPEG，15s/帧 |
| 采集端内存占用 | < 120 MB | 严格控制 CameraX 与缓存开销 |
| 连续运行发热与稳定性 | 3 小时连续抓拍手机表面温升 < 4℃ | 零视频编码，纯静态图片捕获 |
| 断网队列最大容量 | 500 帧（约 2 小时离线记录） | 超过后 FIFO 自动淘汰旧帧 |
| 心跳超时告警时延 | 设备掉线后 180s ~ 240s 内触发推送 | 避免因短暂网络抖动造成误报 |

## 七、合规与隐私约束

1. **儿童个人信息最小化采集**：机位物理规避正脸，画面仅限于桌面与手部动作，不采集环境声音与家庭其他成员；
2. **数据留存周期强管控**：OSS 中的帧图片在上传 90 天后通过生命周期规则自动物理删除；服务端提取的结构化特征长期保留；
3. **未成年人监护人知情权**：设备绑定与注销权限严格归属于 Guardian 账号；
4. **账号注销物理擦除**：家庭注销时，该设备上传的所有历史图片与元数据 24 小时内物理清空。

## 八、安全与防护约束

| 编号 | 风险类型 | 约束要求与防护策略 | 优先级 |
|---|---|---|---|
| S-S01 | 设备伪造与未授权上传 | Cam 端使用长效 `device_token` 鉴权，且必须与 `family_id` 强绑定 | P0 |
| S-S02 | OSS 预签名 URL 泄露与防盗刷 | 预签名 PUT URL 限制有效时长为 5 分钟，且绑定具体 Key 路径与文件大小上限（< 2MB） | P0 |
| S-S03 | 本地缓存图片被恶意读取 | 离线暂存图片存储在 Android 内部私有目录（`context.filesDir`），禁止存放在公开 SD 卡空间 | P0 |
| S-S04 | 频繁请求上传 URL 攻击 | 服务端对 `RequestUploadUrl` 接口实施频控（单设备每分钟不超过 10 次请求） | P1 |

## 九、团队与研发分工

- **`duxue-cam`（Android / Kotlin）**：
  - 负责 CameraX 抓拍、Foreground Service 保活、Room 本地离线队列、OSS 直传、心跳上报与扫码绑定；
- **`duxue-server`（FastAPI + Celery + OSS）**：
  - 负责绑定邀请码生成与校验、OSS 预签名 PUT URL 签发、帧元数据入库、心跳监控与掉线判定告警；
- **`duxue-app`（Flutter）**：
  - Guardian 端负责设备绑定二维码生成、设备列表与健康状态（电量/在线）展示。
