DDD领域分层

读学 Server 的限界分层全景：纵向看四层依赖（Interface → Application → Domain → Infrastructure，Port 是接缝不是层）；横向看 9 个 Bounded Context 的写所有权与协作。模块化单体，单一事实源为 docs/technical/ddd-overview.md 与 design-server.md。

实线箭头 = Integration Event（Outbox 最终一致） 虚线箭头 = 受权 Query / ACL（同步只读） 蓝 = Core · 青 = Supporting · 黄 = Generic
怎么读这张图先纵向看四层依赖：请求只能从 L1 进入、经 L2 编排、落到 L3 的某个 Context 本地事务，L4 只是 Port 契约的实现。再横向看 L3 内部：实线是可重放的版本化事件（最终一致），虚线是同步只读的受权 Query；任何跨 Context 的“直接改对方表 / 调对方 Aggregate”都是禁止项。

Process Manager 与 Use Case 的区别（L2 内部关系）

维度Use Case（应用服务）Process Manager（如 CompanionCoordinator）
范围单个 Bounded Context 内跨多个 Context / 跨多个步骤
状态无流程状态；一次调用结束即完成有状态：自己持有流程状态（Thread/Run/focus/attempt）
时间跨度单次请求、单个本地短事务跨请求、跨 Turn、长时运行（等待 Ward、超时、重试、Handoff）
一致性强一致：Aggregate + Outbox 同事务提交只保证自身流程状态一致；目标 Context 各自本地事务，靠 fencing / 幂等衔接
领域规则调用一个 Aggregate 的行为，不含规则本身（规则在 Domain）不含任何领域规则；只做路由与流程推进，不得替目标 Context 决策或直写其表
本项目实例ConfirmPlan、ApplyTutorTurn、IngestLearningFactCompanionCoordinator：route → RunInvocation → 收 Outcome → fencing → 推进 / 等待 / 关闭

分类上 PM 与 Commands / Queries / Event Handlers 并列同属 L2；只有 Companion Turn 这条运行时链路里 PM 是调用方。普通请求（建 Ward、确认计划、提交自评）由 Interface 直达 Use Case，不经过 PM。PM 的流程状态落在 L3 的 Companion Context（ConversationThread / AgentRunLink）。

WorkflowDispatcher 是什么、何时经过

问题答案
定位Application Port（ports/companion.py 的 Protocol）+ 过渡实现 SqlAlchemyWorkflowDispatcher；本质是注册表 / 组合根，不是新的一层、不是第二个 Process Manager
作用解耦（Coordinator 只依赖 invoke(RunInvocation) -> WorkflowOutcome，测试可注入 Fake）；按 agent_type 保证恰好一个 Workflow 被执行；分发前校验 Run 的 thread_id / ward_id fencing
不做什么不做意图路由（目标已由 Coordinator 内 IntentRouter 决定，它只是照单分发）；不写领域状态、不调模型、不推进 ProblemRecord
经过的场景仅 POST /companion/turn：决策不是 clarify/safety、且已 start/resume 出一个 Run 时，提交路由事务后执行一轮，随后 record_outcome 收口
不经过的场景clarify/safety 终结回复、取消 Run、SSE 重连 / 查 transcript、普通 REST、Celery 记忆与分析任务

ContextBuilder 与 Port 的归类

对象归类说明
ContextBuilderL2 支撑应用服务无对外入口、不与入口构件并列；被三个 Workflow 在 invoke() 开头调用，按 ContextSpec 经 MemoryFacade 受权查询组装最小 ContextEnvelope（预算裁剪、脱敏、freshness），绝不直读业务表
OutputValidatorL2 支撑应用服务与 ContextBuilder 成对：一个管模型调用前喂什么，一个管调用后候选能不能过；均无状态、被 Workflow 调用
WorkflowDispatcherApplication Port（纯抽象 Protocol）小写 interface（编程抽象）：只有 invoke 签名 + RunInvocation / WorkflowOutcome 数据契约；Coordinator 只依赖它，具体分发类运行时注入
Interface 层（L1）大写 Interface（架构层）面向外部 Actor 的入站适配（FastAPI/SSE、Event Consumer），有 HTTP / DTO / 鉴权语义；Port 没有这些，它只是进程内构件间的调用契约，不构成一层

各层职责速览

层包含什么禁止什么
L1 Interface — app/apiFastAPI/SSE 路由、DTO、依赖注入、Event Consumer Adapter直接操作 Aggregate、Repository 实现或 ORM
L2 Application — app/applicationCommands / Queries / Workflows、Coordinator Process Manager、ContextBuilder、OutputValidator替目标 Context 做领域决策；把模型调用包进 Thread 事务
L3 Domain — app/contexts/*/domainAggregate、Value Object、Domain Service（如 TutorPermitPolicy）、不变量、本地 Domain Event依赖基础设施、ORM、模型 SDK；跨 Context 直写对方表
◇ Ports — app/application/ports（归属 L2/L3，非独立层）Repository / Gateway / Publisher / Checkpoint 等纯抽象 Protocol在 Port 里放业务规则或 SQL 实现
L4 Infrastructure — app/infrastructure + workersSQLAlchemy、Celery/Redis、OSS、AI Gateway、OTel / LangfuseWorker 绕过 Use Case 直接改 Aggregate；把儿童原文打进日志
