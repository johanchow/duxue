# 学生行为分析系统：技术方案设计文档

---

## 一、需求背景

### 核心需求

输入一段约 1 小时的学生学习监控视频，自动分析并输出：
- 各时间段内学生的行为状态（学习、离开、走神/玩耍等）
- 每种状态的持续时长统计

### 核心挑战

这个需求看似简单，实际存在几个难点：

**1. 视觉歧义性高**

"头低下"这一视觉特征可以对应完全不同的行为：

```
头低下 + 手在纸上移动    →  写字（学习）
头低下 + 手在玩积木      →  玩玩具（走神）
头低下 + 身体静止不动    →  发呆 或 看书（难以区分）
```

传统规则（检测姿态关键点）无法可靠区分这些情况，需要模型具备**语义理解**能力。

**2. 场景多样性**

不同学生、不同桌面布置、不同光线条件、不同年龄段——单一规则无法覆盖。

**3. 类别扩展性**

不同机构、不同监控目的，需要的行为类别不同：
- 基础版：学习 / 离开 / 走神
- 扩展版：还需区分「睡觉」「吃东西」「做手工」「阅读」「书写」
- 不同客户可能需要完全不同的类别体系

**4. 数据隐私**

学生视频属于敏感数据，在很多场景下不允许上传至第三方服务器。

## 二、技术方案对比

### 方案零：直接调用 Qwen API（通用模型）

```
图片 ──▶  阿里云 Qwen3-VL API  ──▶  行为标签
         （通用模型，不针对场景）
```

| 维度 | 评估 |
|------|------|
| 上手成本 | 极低，当天可用 |
| 场景准确率 | 中等，无法区分高度相似的行为（如写字 vs 玩玩具） |
| 类别灵活性 | 靠 Prompt 调整，效果不稳定 |
| 数据隐私 | ❌ 视频帧上传第三方服务器 |
| 费用（1小时视频/次） | 约 ¥0.20（Qwen3-VL-8B） |
| 适用场景 | 快速原型验证，对准确率要求不高 |

---

### 方案 B：微调 VLM，类别写在 Prompt 里

用自己的标注数据微调 Qwen3-VL，让模型掌握场景知识；新增类别时修改 Prompt 传入。

```
Prompt（含类别定义）
        +              ──▶  微调后的 Qwen3-VL  ──▶  行为标签
图片（视觉输入）
```

| 维度 | 评估 |
|------|------|
| 场景准确率 | 高，针对具体场景训练 |
| 类别灵活性 | 中等，改 Prompt 即可，但不可控 |
| 数据隐私 | ✅ 模型本地部署 |
| 一次性训练成本 | ¥5~10 + 1~2 小时人力标注 |
| 推理费用（1小时视频/次） | 约 ¥1.5~2（云 GPU 按量） |
| 适用场景 | 类别相对固定，少量场景变化 |

---

### 方案 C：两阶段架构（推荐）

将“看懂画面”和“判断类别”拆成两个独立模块。第一阶段 VLM 只输出结构化行为字段，不做最终类别判断；第二阶段轻量分类层基于这些结构化字段做分类，类别完全在这里定义和维护。

```
单帧图片  ──▶  【第一阶段】微调 VLM（结构化解析器）  ──▶  {"body_pos":"端坐", "hand_action":"握笔书写"...}
                                                                │
                                                      （结构化字段，可解释）
                                                                │
                                             ──▶  【第二阶段】分字段加权嵌入分类层
                                                                │
                                                           行为标签
```

| 维度 | 评估 |
|------|------|
| 场景准确率 | 高（第一阶段），分类精确可控（第二阶段） |
| 类别灵活性 | ✅ 最高，新增/修改类别只改第二阶段，VLM 不动 |
| 多客户支持 | ✅ 第一阶段共享一个模型，第二阶段每客户独立配置 |
| 可调试性 | ✅ 结构化字段可读，出错原因一眼定位 |
| 数据隐私 | ✅ 全部本地运行 |
| 一次性训练成本 | ¥5~10 + 1~2 小时标注 |
| 推理费用（1小时视频/次） | 约 ¥1.5~2（同方案 B）|
| 适用场景 | 多场景、多客户、类别会持续演进的产品 |

---

### 三种方案综合对比

```
                方案零（API）    方案 B（微调）    方案 C（两阶段）
                ─────────────   ─────────────    ─────────────
  准确率              中               高               高
  上手速度            快               慢               慢
  类别灵活性          低               中               高
  多客户扩展          难               中               易
  数据隐私            否               是               是
  月处理 100 个       ¥20             ¥200             ¥200
  月处理 2000 个      ¥400            ¥3000            ¥3000
  月处理 10000 个     ¥2000           ¥8000*           ¥8000*
                                   *自购服务器后大幅降低
```

**选型建议：**

```
需要快速验证想法，对准确率要求低    →  方案零
单一场景，类别固定，中等规模        →  方案 B
多场景/多客户，类别持续变化         →  方案 C（本文档重点）
```

## 三、方案 C 详细设计

### 整体架构

```
│                         离线准备阶段（只做一次）                 │
│                                                                │

│                            （标注：结构化行为字段，value 自由文字）           │
└────────────────────────────────────────────────────────────────┘

┌────────────────────────────────────────────────────────────────┐
│                        在线推理阶段（每次处理视频）              │
│                                                                │
│  新视频                                                        │
│    │                                                           │
│    ▼  每帧一张图片                                                │
│  帧图片序列                                                   │
│    │                                                           │
│    ▼                                                           │
│  ┌─────────────────────────────────┐                            │
│  │  第一阶段：VLM 结构化理解       │ →  {"body_pos":"端坐", ...} │
│  └─────────────────────────────────┘                            │
│    │                                                           │
│    ▼                                                           │
│  ┌─────────────────────┐                                       │
│  │  第二阶段：分类层   │  →  "学习"                            │
│  └─────────────────────┘                                       │
│    │                                                           │
```

### 第一步：图片索引生成

**原理**

训练和推理所需的最小单元是"图片 + 路径索引"，不依赖视频文件。将准备好的图片放入文件夹，运行脚本扫描生成 `frames_info.json`，后续所有步骤以此为输入。

图片可来自任意来源：从已有视频手动截图、手机拍摄、标注平台导出，或直接从监控系统获取的帧图片，均可直接使用。

**图片要求**

| 维度 | 要求 | 说明 |
|------|------|------|
| 格式 | JPG / PNG / WebP | 脚本自动过滤其他格式 |
| 分辨率 | 建议短边 ≥ 320px，长边 ≤ 1280px | 太小看不清细节；太大消耗更多 token，推理变慢变贵 |
| 宽高比 | 不限，常见 4:3 / 16:9 均可 | 极端比例（如 10:1 的长条）会影响 VLM 的图像理解 |
| 文件名 | 不限格式 | 脚本按文件名字母序排列，与内容无关 |
| 色彩 | 彩色 RGB 优先 | 灰度图可用，但细节识别略差 |
| 内容 | 学生应清晰可见、无严重过曝/欠曝、无大面积遮挡 | 标注员和模型都依赖图像质量 |

> 脚本在扫描时会自动检查分辨率，对超出建议范围的图片打印警告，不会强制拒绝。

**执行**

```
python scripts/1_extract_frames.py --folder data/frames
```

**输入 / 输出**

```
输入：data/frames/（图片文件夹，支持 jpg / png / webp）

输出：data/frames_info.json
  每行结构：
  {
    "timestamp":   0,              // 序号，不代表实际时间
    "time_str":    "#0001",        // 显示用编号
    "filepath":    "data/frames/xxx.jpg",
    "description": ""             // 待标注，初始为空
  }
```

### 第二步：人工标注

**原理**

模型微调的本质是：给模型看大量“多帧片段 + 正确结构化输出”的例子，让它学会从连续画面中抽取稳定的行为属性。标注质量直接决定模型上限。

**方案 C 的标注内容**

与旧版“自由描述文字”不同，这里第一阶段直接输出结构化 JSON。建议字段如下：

```
  "body_pos":    "端坐在椅子上",         // 人物整体姿态
  "head_pose":   "头部低下约 45°",       // 头部方向和角度
  "gaze_target": "视线落在练习册上",     // 目光注视目标
  "hand_action": "右手握铅笔横向书写",   // 手部动作描述
  "desk_object": "书本、练习册、铅笔",   // 桌面可见物品
  "seat_status": "坐在座位上",           // 是否在座
  "motion_state":"动作持续稳定",         // 短时内状态是否变化
  "desc_summary":"学生低头专注书写"      // 可选，整体摘要，调试用
}
```

**为什么不限枚举**：固定词表会遮蔽真实细节（"用橡皮擦字"强行归入"写字"反而丢失信息），自由短句让 VLM 表达更丰富，第二阶段用分字段嵌入相似度做语义匹配，天然兼容任意措辞。

7 个字段均参与第二阶段分类，`desc_summary` 仅供人工调试和抽查。

**标注工具选择**

| 工具 | 形式 | 适用情况 |
|------|------|---------|
| 命令行脚本 | 终端输入 JSON 字段 | 1人标注，追求简单 |
| Label Studio | 网页界面 | 多人协作，可配置枚举下拉 |
| 自定义网页工具 | 多帧预览 + 表单 | 定制化需求，体验最好 |

**标注规范**

标注时遵循以下原则：

```
1. 优先标注“5 秒内的主导状态”，不要被瞬时一帧误导
2. 字段值尽量枚举化，避免自由发挥
3. 看不清时明确标 "不可见"，不要猜
4. desc_summary 只做辅助说明，不要替代结构化字段
5. 第二阶段最终类别（如“学习/走神/离开”）可单独记录，但不作为第一阶段主目标
```

**数量要求**

| 目标效果 | 标注数量 | 预计标注时间 |
|---------|---------|------------|
| 验证可行性 | 150 个片段 | 约 1.5 小时 |
| 基本可用（~80% 准确率） | 300 个片段 | 约 3 小时 |
| 生产质量（~90% 准确率） | 800+ 个片段 | 约 6~8 小时 |

**输入 / 输出**

```
输入：720 张帧图片
输出：data/annotations.jsonl
  每行：
  {
    "clip_id": "clip_000123",
    "start_time": 610,
    "end_time": 615,
    "frames": [
      "data/clips/clip_000123/frame_01.jpg",
      "data/clips/clip_000123/frame_02.jpg",
      "data/clips/clip_000123/frame_03.jpg",
      "data/clips/clip_000123/frame_04.jpg",
      "data/clips/clip_000123/frame_05.jpg"
    ],
    "target": {
      "body_pos":    "端坐在椅子上",
      "head_pose":   "头部低下约 45°",
      "gaze_target": "视线落在练习册上",
      "hand_action": "右手握铅笔横向书写",
      "desk_object": "书本、练习册、铅笔",
      "seat_status": "坐在座位上",
      "motion_state":"动作持续稳定",
      "desc_summary":"学生低头专注书写"
    },
    "final_label": "学习"
  }
```

### 第三步：整理训练数据

**原理**

Qwen3-VL 微调需要“对话”格式——把多帧片段包装成一问一答：
- 问题：5 张连续帧 + 固定 Prompt，要求输出结构化 JSON
- 回答：标注好的结构化字段

数据集切分不要按“帧随机打乱”，而应按“视频 / 学生 / 机位”维度切分，避免相邻片段泄漏到验证集造成虚高。

**执行逻辑**

```
annotations.jsonl
      │
      ▼
  过滤：去掉字段缺失严重的条目
      │
      ▼
  格式转换：包装成对话结构
  ┌──────────────────────────────────────────────────────┐
  │  User:  [单帧图片] + "请输出学生行为结构化 JSON"      │
  │  Assistant: {"body_pos":"端坐","hand_action":"握笔书写"...} │
  └──────────────────────────────────────────────────────┘
      │
      ▼
  按视频/学生分组切分（避免相邻帧泄漏到验证集）
      │
      ├── 前 90%  →  dataset_train.jsonl
      └── 后 10%  →  dataset_val.jsonl
```

**输入 / 输出**

```
输入：data/annotations.jsonl
输出：
  ├── data/dataset_train.jsonl  （约 270 帧，用于训练）
  └── data/dataset_val.jsonl    （约 30 帧，用于验证）
```

### 第四步：微调 Qwen3-VL（第一阶段）

**目标**

训练出一个“结构化行为解析器”：输入任意一个 5 秒片段（5 张连续帧），输出稳定的结构化 JSON 字段。

**LoRA 微调原理**

Qwen3-VL 有 70 亿参数，直接修改代价极高。LoRA 的做法是在模型的注意力层旁插入两个极小的矩阵（A、B），只训练这两个矩阵：

```
原始权重矩阵 W（冻结，不参与训练）
        +
  A 矩阵 × B 矩阵（可训练，参数量约为原来的 1%）
        =
        该层最终输出

训练完成后，将 LoRA 矩阵合并回 W，得到完整模型
```

**QLoRA** 是在 LoRA 基础上把原始权重压缩到 4-bit 存储，显存从 14GB 降到约 4~6GB，适合消费级 GPU。

**训练循环**

```
加载 Qwen3-VL-7B（4-bit 量化）
        │
        ▼
插入 LoRA 适配层
        │
        ▼
┌───────────────────────────────────────┐
│           训练循环（重复 N 轮）        │
│                                       │
│  取一批训练数据（单帧图片 + 结构化 JSON）         │
│     │                                 │
│     ▼                                 │
│  模型输出预测描述                      │
│     │                                 │
│     ▼                                 │
│  与标准描述比较 → 计算 loss           │
│     │                                 │
│     ▼                                 │
│  反向传播 → 只更新 LoRA 参数           │
│                                       │
│  每 100 步：在验证集上计算 loss        │
│  保存 checkpoint                      │
└──────────────────┬────────────────────┘
                   │
                   ▼
            LoRA 权重合并
                   │
                   ▼
       output/qwen3vl_parser/  （完整模型，约 15GB）
```

**判断训练是否正常**

```
loss
 2.0 │╲
 1.5 │  ╲
 1.0 │    ╲──
 0.5 │       ╲───
 0.3 │            ─────────  ← 收敛，停止训练
     └──────────────────────

  训练集 loss 持续下降 → 正常
  验证集 loss 同步下降 → 正常
  验证集 loss 开始上升 → 过拟合，提前停止
  loss 完全不动       → 学习率过低或数据格式问题
```

**关键超参数**

| 参数 | 含义 | 建议值 | 调整方向 |
|------|------|-------|---------|
| `lora_rank` | LoRA 矩阵大小 | 8 | 数据多时可加到 16 |
| `learning_rate` | 学习速率 | 2e-4 | loss 不降则调大 |
| `num_epochs` | 训练轮数 | 3 | 过拟合时减少 |
| `lora_target_modules` | 覆盖哪些层 | q,k,v,o | 效果差时扩展到 FFN 层 |

**硬件与时间**

| 设备 | 训练时间（300帧，3轮） | 费用 |
|------|--------------------------|------|
| Mac M4 Pro 24GB（mlx-vlm） | 约 2~4 小时 | 免费 |
| 云 RTX 4090（AutoDL） | 约 30~60 分钟 | ¥2~5 |
| 云 A100 40GB | 约 15~30 分钟 | ¥5~10 |

**输入 / 输出**

```
输入：dataset_train.jsonl、dataset_val.jsonl
输出：output/qwen3vl_parser/（可直接加载的模型目录）
```

### 第五步：搭建分类层（第二阶段）

**这是方案 C 的核心优势所在。**

第一阶段输出的是结构化行为字段，第二阶段再把这些字段映射到业务类别。两者完全解耦，类别的新增、修改、删除只在这里进行，不涉及 VLM。

**第二阶段的三种实现方式**

```
┌──────────────────────────────────────────────────────────────┐
│  方式 1：规则匹配（最简单）                                    │
│                                                              │
│  结构化字段  →  规则判断  →  类别                             │
│                                                              │
│  hand_action=写字 AND gaze_target=书本/作业 → 学习           │
│  seat_status=离座 OR body_pos=离开画面       → 离开           │
│  hand_action=玩物 OR gaze_target=他处         → 走神/玩耍     │
│                                                              │
│  优点：可解释，零成本，立即生效                               │
│  缺点：覆盖不全，需要维护规则                                 │
└──────────────────────────────────────────────────────────────┘

┌──────────────────────────────────────────────────────────────┐
│  方式 2：分字段加权嵌入相似度（推荐）                         │
│                                                              │
│  每个 JSON 字段的 value 单独做 Embedding，                   │
│  与该类别在该字段的参考短句集比较余弦相似度；                  │
│  按字段区分度加权汇总，得出最终类别。                          │
│                                                              │
│  示例权重（hand_action 和 gaze_target 区分度最高）：          │
│    hand_action  × 0.35                                       │
│    gaze_target  × 0.30                                       │
│    seat_status  × 0.20                                       │
│    body_pos     × 0.10                                       │
│    motion_state × 0.05                                       │
│                                                              │
│  类别参考短句（prototypes.yaml，每字段 3~5 句）：             │
│    学习 / hand_action: ["右手握笔书写", "在练习本上做题", ...] │
│    离开 / seat_status: ["不在座位", "画面中无人", ...]        │
│                                                              │
│  新增类别：补充该类别各字段的参考短句即可，无需重训 VLM        │
│                                                              │
│  优点：字段独立比较，不同字段可赋不同权重；                   │
│        value 自由文字，不受枚举约束，泛化性强                 │
│  缺点：需要为每个类别、每个字段准备参考短句                   │
└──────────────────────────────────────────────────────────────┘

┌──────────────────────────────────────────────────────────────┐
│  方式 3：轻量分类模型（精度最高）                              │
│                                                              │
│  结构化字段（+可选 desc_summary） → 小模型分类头  → 类别      │
│                                                              │
│  训练成本极低（表格/文本数据，CPU 即可）                       │
│  新增类别：补充该类样本，几分钟重训分类头                      │
│  模型极小，推理速度快                                          │
│                                                              │
│  优点：精度最高，速度快，成本极低                             │
│  缺点：需要维护二阶段训练数据                                 │
└──────────────────────────────────────────────────────────────┘
```

**新增类别的操作流程对比**

```
                 方案 B（Prompt）       方案 C（分类层）
                ─────────────────      ───────────────────────
 新增「睡觉」    1. 修改 Prompt          1. 为各字段补充参考短句
                   加入「睡觉」定义         body_pos: "趴在桌面"

                   是否理解正确          2. 加入 prototypes.yaml
                3. 准确率不稳定，        3. 立即生效，无需重训 VLM
                   依赖模型"理解"

 耗时             几分钟                  几分钟（规则/嵌入方式）
 稳定性           不确定                  确定，可控
 VLM 是否重训     否                      否
```

**输入 / 输出**

```
输入：第一阶段输出的结构化字段（+ 可选 desc_summary）
     + 类别定义配置（规则 / 原型模板 / 分类模型）
```

### 第六步：批量推理与时间轴生成

**推理执行逻辑**

```
        │
        ▼
  时序平滑（滑动窗口投票，消除孤立噪声帧）
```

### 新增类别的操作流程

**使用规则匹配或分字段嵌入相似度方案时：**

```
发现新行为「趴桌睡觉」需要识别
        │
        ▼
为各字段补充参考短句（自然语言，无需枚举）
  body_pos:   "头趴在桌面上"
  gaze_target:"眼睛闭合"
  hand_action:"手臂交叉，静止"
  motion_state:"长时间静止不动"
  ...
        │
        ▼
加入分类层配置文件（无需改动 VLM）
        │
        ▼
立即生效，下次推理自动识别「睡觉」类别
```

**VLM 何时需要重新训练？**

```
需要重训的情况：
  ✗ 摄像头角度发生大幅变化（从正面改为俯拍）
  ✗ 场景变化极大（从小学生换成大学生，桌面完全不同）
  ✗ 结构化解析质量明显下降（第一阶段字段输出不稳定）

不需要重训的情况：
  ✓ 新增/修改/删除行为类别
  ✓ 新增一位新学生（同样的桌面场景）
  ✓ 调整某类行为的判断标准
  ✓ 不同客户需要不同的类别体系
```

### 两步法是不是最佳方案？

结论要分场景看：

- **如果目标是当前项目落地**：两步法是非常好的平衡方案。它兼顾了本地部署、可解释、类别可扩展、多客户复用这几个核心要求。
- **如果目标是极致准确率**：两步法不一定是绝对最佳。理论上，类别固定且训练数据足够多时，端到端的视频分类模型可能比“两步拆开”更高。
- **如果目标是持续演进**：两步法通常优于端到端方案，因为新增类别时只动第二阶段，不必频繁重训 VLM。

因此，本文档推荐的结论应是：

```
对“学生行为分析”这个项目的当前阶段，
两步法不是理论上的绝对最优，
但它是工程上最稳妥、最可维护、最容易扩展的方案。
```

可简单理解为：

| 目标 | 更优方案 |
|------|---------|
| 快速验证、可解释、类别经常变 | 两步法（本文方案） |
| 类别长期固定、追求极致精度 | 端到端视频分类可进一步评估 |
| 多客户复用、长期维护 | 两步法明显更优 |
