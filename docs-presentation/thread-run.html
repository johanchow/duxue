陪伴对话如何接得住：换话题不串话，中断了能续上

一句话设计：Ward 看到一条连续对话，系统内部却有多个可暂停、可恢复、可作废的工作（Run）；Thread 是这条对话的唯一仲裁者，Coordinator 是流程的推进者，模型只是被围栏约束的候选生产者。 本图只画同一抽象层的逻辑概念（聚合、值对象、流程角色与裁决规则）；数据库表、SSE、HTTP 状态码等物理落地只在契约栏中以代码类型标注。

技术难点：这个编排层必须同时解决的两个问题

难点 1 · 连续性 一条对话，多个随时切换的工作，如何不串话？

孩子感知到的是一条连贯对话，背后却是计划、答疑、复盘等多个可并存、可暂停的 Run：上一题还没做完，又说“帮我安排明天复习”。若每个工作都能直接对孩子说话，回复必然互相覆盖、指代错乱。

难点在于：必须有一个唯一仲裁者决定“此刻谁有回复权”，且切换必须是原子裁决，不能靠各工作自行抢占。
难点 2 · 不可信输入 意图与内容都出自模型，状态一致性由谁负责？

“这句话该进哪个场景”只能靠模型理解语义，但模型会误判、会迟到、会被注入。若让它直接建 Run、改状态、写事实，一次幻觉就能污染业务数据；可若事事都要代码裁决，又不能把昂贵的模型调用包进数据库事务里慢慢等。

难点在于：提议与裁决必须分离——先用短事务把路由定下来，再放模型在事务之外执行。

给架构师的三个结论

1 · 单一回复权是“不串话”的前提
例子答疑 Run 还在等孩子提交第一步，孩子突然说“帮我安排明天复习”。Coordinator 在同一事务里把答疑 Run 转 paused、新建 Planning Run 并换 focus；随后旧答疑的流式结果迟到到达，因 focus 已变更被直接丢弃——孩子自始至终只看到计划场景的回复。

多个 Run 可以并存、暂停、等待，但同一时刻只有 focus Run 能对 Ward 说话。焦点切换是一次原子裁决（换 focus + 推进 Thread 版本同事务提交），不是各 Workflow 自行抢占。

2 · 先裁决，后执行，慢模型才不锁状态
例子网络抖动让同一条消息带着同一 command_id 提交了两次：第二次在 _restore_idempotent 就命中已完成的结果直接返回，不再调模型、不再建 Run。而正常路径里，路由（建 Run、写 Ward 原话、version+1）先短事务提交，耗时数秒的模型调用发生在这之后、事务之外。

一轮 Turn 先完成路由裁决并固定世代，再开始昂贵且不可回滚的模型执行。短事务只做确定性的事，慢且不可信的事全部推到事务之外——一致性与响应速度因此不必二选一。

3 · 世代围栏让“迟到”从事故变成常态处理
例子孩子点取消后，在途的答疑调用才返回一份“完美”的引导文案：record_outcome 校验发现 Run 已 cancelled、focus 已清除，四元组不匹配，于是只留一条 late_outcome_discarded 审计——内容再对也不上屏。反过来，SSE 只是断线时，孩子带最后 sequence 重连同一 attempt 即可重放，不会被误判成取消。

Outcome 必须携带 run + turn + attempt 并仍是 focus 才被接受。系统不判断迟到结果“对不对”，只判断它“还属不属于现在”——异步系统里，世代正确性优先于内容正确性。
