# 家庭共管成员

## 做什么 / 为什么

让两位家长各用自己的账号，查看并管理同一份孩子档案。日常权限相同，共管关系和整份孩子数据的清理由档案创建者管理。

## 验收标准

- [x] 创建者在「我的 → 共管成员」选一个孩子，按对方的登录邮箱发起邀请。对方登录后在同一入口看到孩子和邀请人，确认后孩子出现在首页。未接受前无孩子访问权限。
- [x] 双方均可查看现有 Guardian 可见的报告和学习情况，编辑孩子姓名、年级，并管理学生 App 绑定和学习设备。两人操作的是同一份档案。
- [x] 创建者可查看成员和待接受邀请、取消邀请、移除成员。成员可以主动退出，无法邀请或移除他人，也无法清除整个孩子的数据。撤销关系后，服务端拒绝后续访问，App 刷新后移除对应入口和视图数据。
- [x] 邀请仅适用于选定孩子和目标账号，有有效期。重复接受不会重复建关系，已取消或已过期的邀请无法接受。新建的孩子需单独邀请。
- [x] 现有孩子及学生登录绑定继续可用。迁移前检查已有多家长绑定，结合可验证的创建信息或人工确认确定创建者，避免根据不可靠的字段猜测。

## 实现计划（Gate 1）

- 服务端沿用 Guardian–Ward 绑定做日常鉴权，在身份域补创建者标识和独立共管邀请。验证目标邮箱、邀请状态和权限，在事务中接受邀请。梳理档案清除和换绑相关入口，明确哪些操作只由创建者执行。
- Flutter 将「共管成员」占位卡片接入邀请收件、发起和成员管理。孩子设置补姓名和年级编辑，新增或失去关系后刷新孩子列表和相关页面状态。
- 更新用户 PRD 和技术设计，统一家庭共管的授权规则。按服务端 README 核查本地业务 PostgreSQL 的迁移状态。
- 只新增服务端单元测试和 Flutter widget 测试，覆盖邀请接受、撤销、过期、越权、编辑和列表刷新。运行现有相关测试及静态检查。
